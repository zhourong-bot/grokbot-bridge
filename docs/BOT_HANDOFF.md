# Bot 寻址与交接 runbook —— 怎么保证"发对 bot"、"换对话后接得过去"

## 一句话模型
**逻辑角色名(稳定地址) ↔ 物理 webhook URL(可重绑)**,中间隔一层 `botreg` 注册表;
**每次(重)绑定都必须过一次回声握手才生效**。我的派活永远只寻址角色名,不碰 URL。

- `send_doorbell.sh --bot <role> ...` → botreg 解析 role 当前 URL/KEY。
- **硬门**:角色未验证(`verified_at` 空)→ `send_doorbell` **拒发正式任务**(exit 4)。只有握手模式(`GROK_HANDSHAKE=1`)能对未验证角色发探针。
- 判据只有一个:**回声握手**。不是 HTTP 200(它只说 automation 端点收下了,不说落到哪个 bot)。

## 为什么这样能解决"交接错 bot"
- 老 webhook 永久绑当初建它的那个 bot/对话。多 bot 出现后,一个写死 URL 必然发错。
- 现在:每个 bot 对话各自建自己的 webhook routine → 各自一条 URL → 注册成不同角色。
- 换绑/新增任何 URL,`botreg set` **立即把该角色打回未验证**,不重握手就发不出正式任务。
- 握手用**唯一暗号**:只有真正收到该 webhook 的那个 bot 知道暗号;它把暗号原样经桥送回 + 自报身份,我才标验证。绑错的 bot 回不出我预期的身份 → 当场暴露。

## 路线 A —— 人肉转发(今天就能用,100% 不会错 bot)
webhook 完全不参与。"对的 bot"由你亲眼选对话保证。
1. 我在对话里打一段**带暗号**的报备(如 `PING-7F3A ...`)。
2. 你复制 → 贴进目标 bot 对话 → 把它的回复贴回给我。
3. 我确认回复里带 `7F3A` 才算"收到+是这个 bot"。看不到暗号 = 未确认 = 当没送到。
- 代价:每轮两次复制粘贴。最快、最不会错,适合"守护者及时给方向"的项目。

## 路线 B —— 给某 bot 绑专属 webhook(半自动,要你去面板抄一次)
1. 在**目标 bot 对话**里建一个「webhook 触发」routine → 拿到新 URL + 密钥(绑的就是这个对话)。
2. 你把 URL/密钥给我,我注册:
   ```
   python3 botreg.py set <role> "<url>" "<key>" "这个bot是干嘛的"
   ```
   注册即未验证。
3. **必做握手**:
   ```
   bash handshake.sh <role>
   ```
   我发 `PING-xxxx`,该 bot 必须回带 `xxxx` + 自报身份 → 暗号经桥落回才标 `✅已验证`。
4. 之后 `send_doorbell.sh --bot <role> "任务"` 才能发出去(未验证会被硬门拦)。

## 交接接管 —— 换对话后 bot 怎么"对应接过去"
当同一个角色的工作从旧 bot 对话搬到新 bot 对话:
1. 新对话建自己的 webhook → `botreg set <role> <新url> <新key>`(**自动作废旧验证**)。
2. `bash handshake.sh <role>` 重握手(暗号回来才信新绑定)。
3. **上下文续接靠锚文件**:角色的项目锚文件(如 `<你的项目目录>/HANDOFF.md`)留在本机,
   新 bot 读同一锚文件即接上进度——因为所有 bot 都能直接读写本机文件。角色名不变,我的派活不用改。
- 疑似绑错/交接未确认时:`python3 botreg.py unverify <role>` 手动打回未验证,强制重握手。

## 纪律(硬性)
- **绝不拿 HTTP 200 当"送达对的 bot"**;只认暗号经桥落回。
- 角色**只在 verified 状态可用**;任何重绑、或怀疑换了对话,先 `unverify` 再 `handshake`。
- 一个角色 = 一个 bot 对话。新对话就是新角色(或对老角色重绑+重握手),不共用 URL。
